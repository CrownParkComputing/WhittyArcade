Modular arcade emulator

WhittyArcade.

A standalone emulator for Sega, Namco and Capcom arcade hardware — built on one idea: each board is a self-contained module, and each game is data.

What it is

A curated shelf of arcade boards, run well.

WhittyArcade emulates a hand-picked set of arcade platforms — the Sega Model 1 and Model 2 3D boards, Namco System 22 and the Ridge Racer family, and a bench of classic Z80/6809 games — with real CPU and DSP cores, not recompilation.

It draws a hard line between three things: the emulated hardware, the application that wires a board to input, audio and settings, and the host output layer that owns the window. That separation is what lets the codebase stay small while every board keeps its own identity. MAME is the reference throughout — WhittyArcade keeps MAME’s short-names as durable keys and uses it as the accuracy oracle when a board is brought up.

Different question, different shape

How it differs from MAME

MAME preserves everything; WhittyArcade runs a shelf. That single difference in goal is why the two are built so differently.

Goal
MAME

Preserve every arcade machine ever made — tens of thousands of drivers, documentation-grade accuracy.

WhittyArcade

Run one curated set of boards really well, with a clean, teachable architecture and a player / operator front-end.

Unit of code
MAME

One driver per machine. A game is C++: a GAME() entry, a machine config and address maps.

WhittyArcade

One module per board, holding hardware only. A game is data — a per-game profile the ROM loader fills and the hardware reads.

Adding a game
MAME

Write or extend a driver in the shared machine framework.

WhittyArcade

Add a catalog row, and — if the hardware already exists — a profile. No new board switch anywhere.

Binary shape
MAME

One monolithic binary over a universal device tree.

WhittyArcade

Each board is its own static library, linking only the CPU / chip cores and sub-boards it actually uses. The app links the boards.

Shared hardware
MAME

Devices shared through the global machine framework.

WhittyArcade

Sub-boards are first-class and board-neutral: Model 1’s sound & I/O boards are reused by Model 2, the System 24 tile layer is shared, and no board references another board’s games.

Switching game
MAME

Tears down and rebuilds the whole machine — often the window with it.

WhittyArcade

Only the emulated cabinet is destroyed and rebuilt, in a deterministic order. The host window and video worker survive.

ROM handling
MAME

Strict per-set / CRC audit against a fixed rompath.

WhittyArcade

Reads current-MAME ZIPs, extracted sets and CHDs directly from dedicated folders. Merged, split and non-merged layouts work without an import, copy or repack step.

These aren’t competitors. MAME answers “can this machine be preserved and documented?” WhittyArcade answers “can this shelf of boards share one clean, composable codebase and a good front-end?” — and it leans on MAME to get each board right.

Focused desktop app, different scope

How it differs from FinalBurn Neo

FinalBurn Neo offers a much broader multi-system catalog and a mature Libretro ecosystem. WhittyArcade concentrates on a smaller group of explicitly integrated arcade boards, cabinet modes and operator workflows.

Catalog
FinalBurn Neo

Broad arcade, console and computer coverage through standalone ports and a widely used Libretro core.

WhittyArcade

A curated Windows / Linux shelf that includes selected Namco and Sega 3D boards alongside classic 2D hardware.

ROM workflow
FinalBurn Neo

Uses sets matched to the installed FBNeo version, with official DAT and rebuild guidance.

WhittyArcade

Reads its supported current-MAME ZIPs, extracted sets and CHDs directly from ROM folders without importing or repacking them.

Multiplayer
FinalBurn Neo

The Libretro core participates in RetroArch’s broader netplay and frontend feature ecosystem.

WhittyArcade

Two open apps discover each other and launch a shared supported 2P game. Sega Rally alone uses a native two-cabinet hardware link.

Cabinet UI
FinalBurn Neo

Broad input and DIP coverage with frontend features varying between standalone and Libretro use.

WhittyArcade

One built-in launcher for ROM folders, controls, pause/operator settings, high scores and native-aspect single/twin output.

Routing lives in data, not switches

A lightweight catalog is the single source of truth for board names, menu order, ROM-library directories and supported games — and it links no ROM loader. A separate probe asks each board loader to identify an archive and hand back a stable short-name. There is exactly one board-to-session factory switch in the whole program.

The host survives a ROM change

On a game switch the outgoing session stops board-owned producers first, fences and clears queued video work, drops its input watch, flushes durable operator data, and only then releases CPUs and RAM. The next board is built from fresh objects. The shared window and presenter never tear down — so nothing leaks between games, and the GPU driver is never re-initialised mid-session.

Threads follow the hardware

Each board defines its own hardware-safe hand-off boundaries: System 22 advances its 68020, both C71 DSPs and the C74 in bounded slices; Model 2 owns i960, TGP and geometry on one worker while its sound board runs on another. A CPU is never placed on an unconstrained host thread when it shares timing-sensitive RAM or interrupts.

Invariants, enforced by tests

MAME short-names are durable keys for ROMs, NVRAM and scores; every board type has exactly one descriptor and at least one game; unknown archives never fall through to a default board. A factory test repeatedly builds and destroys every catalogued board against one shared video worker.

What you get

Features

Emulation

Real CPU & DSP cores

i960, NEC V60, MC68020, 68000, 6809, Z80, M37710 and the Model 1/2 TGP geometry processors — interpreted and cycle-scheduled, not recompiled.

Output

Three presenters

OpenGL, Vulkan or a software renderer, all sharing one aspect-correct, letterboxed present path so the board’s image is never stretched.

Displays

Native twin-screen output

Single screen, two bordered fullscreen panes, two windows on one desktop, or one window per monitor — always fitted from the board’s native raster without stretching.

Network

Automatic two-player play

Open WhittyArcade on two computers and the launchers discover each other, elect Player 1 / Player 2 and share one installed-game menu with no IP or role setup.

Light guns

On-screen crosshairs

Per-player coloured gun sights for Virtua Cop and Time Crisis, mapped through the real board’s gun ADC — both players read and drawn every frame.

Input

Remappable controls

SDL3 gamepad, keyboard and mouse with instance-ID hotplug, plus an in-app capture UI to rebind any control per game.

Operator

DIP & NVRAM

An operator settings menu with DIP layouts, plus per-set EEPROM / NVRAM persistence generated from catalog metadata.

Scores

High-score capture

High-score tables are captured and persisted per set, keyed on the same durable MAME short-name as everything else.

Library

ROM folders & audit

Drop merged, split or non-merged sets into the ROM folder and CHDs into the media folder. WhittyArcade reads them in place and audits each set against its loader.

Lifecycle

Clean game switching

Deterministic teardown, a persistent host worker, pause / resume and frame pacing — switch games without restarting the process.

Two players, two screens

Dual-screen output, in detail

Player 1
Player 2

Selectable at launch. Choose Single Screen, bordered twin fullscreen, two windows on one desktop, or one window on each physical monitor.

Proper resolution on every screen. Twin output preserves the exact board raster with one integer multiplier on both axes. Galaga remains 224×288; Shinobi remains 320×224.

Who’s who. Each screen carries a small Player 1 / Player 2 identifier in the corner, so the pair know which screen is theirs.

Display mode is independent of networking. Twin output can mirror one local cabinet. The Multiplayer menu is what connects two applications and routes the remote player’s controls.

Two apps, one game

Network multiplayer without manual setup

Player 1 · authoritative game
Player 2 · connected

Open both apps and play. The launchers discover each other, elect roles and show a shared Multiplayer list containing games installed at both ends. Player 1 selects once and Player 2 follows automatically.

Alternating-turn network play. Galaga, Galaxian, Moon Cresta, UniWar S, Phoenix, Shinobi, Ghosts’n Goblins and Pac-Mania run one authoritative arcade session. Both players see the same picture and score; control ownership follows the original cabinet’s turn.

Simultaneous network play. Virtua Cop and Virtua Cop 2 accept both players’ controls every frame, including their independent gun inputs.

Native cabinet link: Sega Rally only. Sega Rally Championship is the sole native linked-cabinet title currently advertised. It runs two emulated Model 2 cabinets using Sega’s real link protocol and automatically selects CAR1 / CAR2 EEPROM roles. Other games use WhittyArcade’s efficient authoritative-video and remote-input link, not a pretend hardware link.

Where the ROMs live

ROM folders

WhittyArcade reads supported current-MAME archives, extracted sets and CHDs directly from dedicated platform data folders. Nothing is imported, copied, extracted or repacked.

  1. Drop in supported ZIPs or extracted sets under roms, and disc media under chd.
  2. Keep your layout. Merged, split and non-merged MAME collections are resolved in place.
  3. Audit from ROM Folders in the launcher, with missing or wrong files reported by name.
  4. No import step. Your source archives are never copied, modified or repacked.
# Linux folders
~/.local/share/WhittyArcade/roms/
~/.local/share/WhittyArcade/chd/

# audit the whole library
WhittyArcade --audit-roms

# list supported sets and requirements
WhittyArcade --list-roms

# Windows folders
%LOCALAPPDATA%\WhittyArcade\roms
%LOCALAPPDATA%\WhittyArcade\chd

Build & run

Getting started

WhittyArcade is C++17 with an SDL3 host layer, and builds on Linux and Windows. Each board compiles to its own static library, and the CPU / chip cores are vendored as small libraries the boards link on demand.

Configure with CMake, build, then place supported sets in the displayed ROM / CHD folders. A suite of unit and real-ROM integration tests covers the catalog, session lifecycle and every board loader.

cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j

# tools live behind flags
build/WhittyArcade --list-roms
build/WhittyArcade --audit-roms

# tests
ctest --test-dir build --output-on-failure
